# Загрузка каталога и справочников 1С

Все команды запускаются из корня проекта с активным venv и загруженным окружением. Примеры ниже относятся к DEV. Для PROD одновременно замените окружение, роль и явные параметры на prod / veqta_prod.

## Каталог СИЗ

Каталог не является кадровой выгрузкой. Основной способ заполнения и изменения — штатный Django Admin, см. [directories.md](directories.md). После чистой установки каталог пуст. Для массового первоначального заполнения можно подготовить собственный CSV; готового списка позиций и фиксированного количества в коде нет.

CSV: UTF-8 с необязательным BOM, разделитель `;`, ровно шесть колонок:

```text
code;name;category;validity_days;sort_order;is_active
```

| Поле | Условие |
|---|---|
| `code` | Непустой уникальный код, до 32 символов |
| `name` | Утверждённое название, до 120 символов |
| `category` | Утверждённая категория, до 64 символов |
| `validity_days` | Целое число от 1 до 32767 календарных дней |
| `sort_order` | Целое число от 0 |
| `is_active` | 0 или 1 |

Сохраните CSV вне исходников либо в исключённом каталоге `private/`. Укажите фактическое проверенное число строк:

```bash
read -r -p 'Подтверждённое число позиций каталога: ' CATALOG_COUNT
```

```bash
python manage.py workwear_load_catalog private/approved_catalog.csv --environment dev --database-name veqta_dev --expected-count "$CATALOG_COUNT"
python manage.py workwear_load_catalog private/approved_catalog.csv --environment dev --database-name veqta_dev --expected-count "$CATALOG_COUNT" --apply
```

По умолчанию команда лишь проверяет файл. При apply она создаёт недостающие записи одной транзакцией; совпадающие сохраняет, конфликтующие не перезаписывает. Обязательный `--expected-count` должен совпасть с числом строк файла. Команда не назначает состав каталога и не ограничивает его исходным числом позиций.

## Контракт 1С

Используются только три файла: `Employees.csv`, `Positions.csv`, `Units.csv`. Кодировка UTF-8 с необязательным BOM, разделитель `;`. Дополнительные колонки допускаются, обязательные заголовки не должны повторяться. Не используйте кадровые файлы в качестве тестовых примеров или содержимого репозитория.

| Файл | Обязательные колонки |
|---|---|
| `Employees.csv` | `extId;tabNumber;name;positionExtId;unitExtId;orgExtId;orgName` |
| `Positions.csv` | `extId;name` |
| `Units.csv` | `extId;name;orgExtId;orgName` |

`extId` сотрудника, должности и подразделения — UUID. `orgExtId` — устойчивый идентификатор организации до 255 символов без пробелов; его формат UUID не навязывается, регистр нормализуется в нижний. Он передаётся из парсера в публикацию и сохраняется в `Organization.external_id`. `tabNumber`, имя и организация сотрудника обязательны. Пустые ссылки на должность или подразделение допустимы и отражаются в счётчиках. Непустые ссылки должны разрешаться. Подразделение ищется по паре GUID и организация. Конфликтующие непустые атрибуты одного GUID отклоняются; одинаковые и дополняющие строки объединяются.

Один файл ограничен 128 МиБ, число строк — установленным в адаптере пределом порядка миллиона. Архив читается без распаковки: три CSV должны лежать непосредственно в корне tar.gz, быть обычными файлами и не повторяться. Символические ссылки и вложенные пути не используются.

## Приём справочника

Сначала проверьте каталог файлов без записи:

```bash
python manage.py workwear_import_1c private/source --environment dev --database-name veqta_dev
```

Изучите `unique_current_employees`, а также `publication_review`: предыдущий импорт, количество выпавших GUID и их SHA-256. Эти результаты могут содержать кадровые идентификаторы; не публикуйте их в исходниках или общедоступных журналах.

Для приёма нужен неизменяемый снимок:

```bash
tar -czf private/source.tar.gz -C private/source Employees.csv Positions.csv Units.csv
python manage.py workwear_import_1c private/source.tar.gz --environment dev --database-name veqta_dev
```

Заполните параметры по фактическому dry-run и подтверждённой дате выгрузки, затем примите пакет. Значение 0 для предыдущего импорта означает только первое принятие:

```bash
read -r -p 'Подтверждённое число сотрудников: ' EMPLOYEE_COUNT
read -r -p 'ID последнего импорта, 0 для первого: ' PREVIOUS_IMPORT_ID
read -r -p 'Дата выгрузки YYYY-MM-DD (например 2026-11-18): ' EXPORT_DATE
python manage.py workwear_import_1c private/source.tar.gz --environment dev --database-name veqta_dev --apply --expected-employee-count "$EMPLOYEE_COUNT" --expected-previous-import-id "$PREVIOUS_IMPORT_ID" --source-export-date "$EXPORT_DATE"
```

Если сотрудники выпадают из текущей выгрузки, передайте дополнительно `--confirm-missing-current-sha256` с точным digest из проверенного dry-run. Не добавляйте эти параметры без проверки причины.

Публикация блокирует справочник и выполняется одной транзакцией. Организации из Employees и Units сопоставляются по `orgExtId`. Неизвестные создаются с запрещённым созданием заявок. При прежнем ID новое `orgName` обновляет `source_name` организации и текущие кадровые атрибуты, но не название, заданное в Admin.

Если в базе есть несопоставленная запись с тем же названием, публикация останавливается: задайте её `orgExtId` через Admin и повторите приём. Импорт не объединяет организации по названию и не изменяет уже заданный внешний ID. Внешний ID требуется у ручной записи до первой публикации её сотрудников. Приём того же последнего пакета остаётся идемпотентным; чтобы обновить сведения, нужна следующая новая выгрузка.

 Новые GUID добавляются, существующие обновляют имя, табельный номер, должность и подразделение. Исчезнувшие сотрудники не удаляются, но новое включение в заявку им недоступно. Смена организации без нового GUID отклоняется. Снимки ранее созданных заявок не переписываются.

Повтор последней тройки хешей с той же датой возвращает already_accepted без нового импорта. Более старая уже принятая тройка отклоняется; новый снимок с более ранней датой источника тоже отклоняется. Дата приёма не заменяет дату источника. Период табеля из этих трёх справочников не выводится и в модели импорта не хранится. Подтверждённая календарная дата обязательна в формате `YYYY-MM-DD`: без времени, часового пояса или искусственного `T00:00:00+03:00`.

Новая исправленная выгрузка с другим SHA-256 допускается в тот же календарный день при точном предыдущем import ID. Более ранний день отклоняется, а повтор той же тройки SHA с той же датой идемпотентен.

Чистая схема `0001_initial` использует `EmployeeImport.source_export_date` типа Django `DateField` / PostgreSQL `date`. Время и часовой пояс не хранятся. **Это изменение требует нового cold start:** обновлённый код нельзя применять к существующей базе с прежней колонкой `source_exported_at`. Прежде чем пересоздавать DEV, сохраните проверенную резервную копию, исходные CSV, каталог СИЗ, список разрешений и пользователей, а также нужные заявки; затем выполните плановое пересоздание в изолированном контуре. Не применяйте `migrate --fake` и не удаляйте действующую базу без подтверждённого восстановления.

При ошибке количества, версии справочника, ссылок или SQL-ограничения весь apply отменяется. Исправьте источник или подтвердите правильный снимок и повторите dry-run. Отключать триггеры и исправлять рабочие таблицы напрямую не требуется.
