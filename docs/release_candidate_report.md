### Места, условия и причины

A-01: `deploy/postgresql/dev.sql:6`, `prod.sql:6`, `config/database.py:7`, `veqta_initialize.py:17`. Исходный bootstrap создавал прикладную роль владельцем; это давало право изменить защищённую схему независимо от наличия триггеров. Исправлены bootstrap, выбор роли команды, генерация env, apply и инструкции восстановления. Владелец устанавливает схему обычным Django migrate; своей системы миграций нет. Исходные атрибуты роли сохранены в baseline-roles.json, итоговые — roles-final.json.

A-02: `workwear/static/workwear/js/core.js:72`, `editor.js:248`, `overlays.js` (карточка). Воспроизведение исходного core.js из исходного SHA возвращает старые имя/категорию/срок первой записи вместо текущего каталога; результат сохранён в historical-core-reproduction.json. Браузерный сценарий добавляет сотрудника А, сохраняет назначение, меняет имя/категорию/365 → 90 дней через настоящий Admin, добавляет Б и сохраняет. Обе записи сверяются с PostgreSQL, списком, матрицей и карточками; затем позиция отключается, заявка завершается и перезагружается. А остаётся со своим первым снимком, Б — со вторым. Изменение каталога не переписывает назначения. Заголовок явно подписывает текущий срок как «каталог». При отсутствии права чтения каталога колонка обозначается стабильным ID, без заимствования чужого снимка.

A-03: `scripts/create_config.py:10`, `server_checks.sh:21/72/80`, `server_apply.sh`, `deploy/nginx/veqta.conf`, `veqta-http.conf`, `deploy/letsencrypt/renew-nginx.sh`. Домены больше не определяются независимыми константами. DNS-имя проверяется по длине и составу меток. Пропущенные реквизиты не наследуются из родительского окружения. Перед migrate сравниваются ENV, DB_NAME, DB_USER, host, port, SSL и фактическое подключение владельца. Тесты проверяют недопустимые/отсутствующие значения, чужую БД/окружение/роль, несовпадение PostgreSQL, повторный генератор, повторный apply и точное восстановление прежнего файла сайта без reload при ошибке nginx -t. Соседний сайт остаётся прежним. Нативный Nginx 1.26.3 проверил оба шаблона для двух собственных доменов; только listen-порты и пути сертификатов заменены на изолированные тестовые.

A-04: `editor.js:253/259`, `workwear/static/workwear/app.css`. Заголовки строк связаны с колонкой и категорией через headers; colgroup соответствует только соседним позициям. CSS уточнён для tbody th, чтобы семантика не меняла оформление сотрудника. Самодельного ARIA-grid нет. Фокус, прокрутка, один tabindex=0 и адресная замена строки проверены в браузере.

## Что сохранено и почему

PostgreSQL уже корректно сохраняла индивидуальные снимки; дефект A-02 относился к источнику отображения. Модели, сервисы и `0001_initial` не менялись. Осталась одна начальная миграция Workwear с 10 функциями, 13 guards и двумя составными FK. Перенос старых данных и --fake не добавлялись.

Пользователи, группы, разрешения, формы и Admin остаются штатными Django. Организации, названия, категории и сроки СИЗ — данные БД. Перечней рабочих организаций или одежды в приложении нет. Каталог на 62 позиции в тесте подтверждает отсутствие привязки к первоначальному количеству; 30 колонок — технический бюджет страницы, а не размер справочника.

При целевом поиске не подтвердились новые основания для переписывания API, импорта, сервисных транзакций или CSS-каскада. Проверены URL, management-команды, шаблоны, общий ctx и делегированные события. После изменения rowWarning удалена ставшая неиспользуемой обёртка editor.itemNames; общий helper остаётся нужен диалогу конфликта. Стабильные публичные маршруты не удалялись из-за отсутствия прямого вызова из текущей страницы. Массовое форматирование и редизайн не выполнялись.

## Полномочия PostgreSQL

| Возможность | Прикладная роль | Владелец схемы |
|---|---|---|
| Владение базой, схемой, таблицами, функциями | Нет | Да |
| Чтение и штатные INSERT/UPDATE/DELETE | Да, с FK/CHECK/guards | Да |
| DDL и штатный Django migrate | Нет | Да |
| Отключение guards / изменение их функций | Нет | Доверенная административная возможность |
| TEMP и TRUNCATE | Не выданы | Возможность владельца; защищённый TRUNCATE отклоняют guards |
| CREATEDB | Нет | Только DEV для Django-тестов |
| SUPERUSER, CREATEROLE, REPLICATION | Нет | Нет |
| Членство приложения во владельце | Нет | Не используется |

Default privileges заданы до migrate; EXECUTE от PUBLIC отозван глобально. SQL-функции остаются SECURITY INVOKER. Сервис получает только env приложения root:veqta-ENV 0640; env владельца root:root 0600 читается отдельным процессом явной операции миграций. Третья роль не нужна: владелец одновременно выполняет штатные миграции.

SQL guards защищают целостность и append-only историю. Они не знают пользователя Django: законный переход закрытой заявки в черновик разрешается сервисом по native permission reopen_request. Прикладные реквизиты БД нельзя выдавать конечным пользователям как самостоятельный интерфейс авторизации. Владельцы PostgreSQL остаются доверенными операторами.

Проверены прямые отказы ALTER/CREATE/DROP, DISABLE TRIGGER, SET ROLE владельца, session_replication_role, TRUNCATE, удаления/правки событий, правок закрытой заявки и чужой организации. Для ожидаемых отказов SQLSTATE сверяется явно. Ни один guard ради испытаний не отключался. Прикладная роль и владелец каждого контура получили отказ CONNECT к базе другого контура.

Счётчики всех 18 таблиц совпали, 13 guards включены, объекты принадлежат владельцу. Приложение читает восстановленные данные и получает ожидаемые отказы DDL, удаления истории и изменения закрытой заявки. Будущий объект владельца получил DML/default grants: INSERT/SELECT/UPDATE/DELETE прикладной ролью прошли. Исходная рабочая инфраструктура для этого не использовалась.

## Проверка серверного стека

Использован существующий tests.acceptance/browser_matrix/browser_support; отдельная система браузерного тестирования не создавалась. `--server nginx` запускает настоящие Gunicorn и Nginx в отдельном временном каталоге и на случайных loopback-портах. Берётся deploy/nginx/veqta.conf; адрес/порты, пути и цель redirect адаптируются к приватному стенду. Системные конфигурации и службы не читаются и не изменяются. Процессы останавливаются по завершении, временные ключи удаляются.

TLS-клиент проверил цепочку через явный тестовый CA-файл и hostname localhost/127.0.0.1. Клиент без доверия к этому CA и клиент с неправильным hostname получили отказ. Проверены HTTP→HTTPS 301, Secure CSRF-cookie, X-Frame-Options DENY, статика, MIME CSS и Cache-Control no-cache. В браузерных контекстах для самоподписанного сертификата включён ignore_https_errors; отдельные положительные и отрицательные проверки TLS выполнены обычным SSL-клиентом. Это не проверка публичного ACME-сертификата.

В первом HTTPS-прогоне WebKit сценарий читателя не дождался появления матрицы. В этом сценарии отсутствовало ожидание завершения входа. Общий sign_in теперь ждёт URL главной страницы до следующей навигации; последующий полный прогон WebKit прошёл. Отказ записи читателю проверяется по JSON-коду forbidden после корректного CSRF, а не только по HTTP 403. Изменять приложение не потребовалось.

## CI и документация

verify.yml запускает обязательные проверки при push/pull_request на Python 3.14.4 и PostgreSQL 18.7. Временные секреты генерируются в runner; серверные реквизиты и deploy отсутствуют. Ручной workflow_dispatch устанавливает Nginx/OpenSSL и выполняет те же сценарии в трёх движках через HTTPS с axe; в Chromium добавляется HTTP-приёмка восьми пользователей. Этот расширенный удалённый прогон пока не запускался; актуальные полные браузерные результаты получены локально. Отдельного браузерного стенда или системы тестирования не создано: расширены tests.acceptance/browser_matrix/browser_support. Статус удалённого Actions-run проверяется отдельно от локального выполнения команд и фиксируется в итоговом manifest.

Обновлены README, architecture, configuration, deployment, installation, operations, testing, workwear и cold_start_report. Предметные справочники остаются в native Admin, инфраструктура — в env/Nginx/systemd. Инструкции учитывают отдельного владельца, первый сертификат, обычный apply, явный migrate, backup/restore и частичные отказы. В отчёте не используются результаты старого кода как подтверждение текущего.

## Дополнение: привилегированные миграции (18.11.2026)

## Непроверенные сценарии и остаточные ограничения

- Развёртывание на целевой Ubuntu, запуск unit через systemd, публичный DNS/ACME/HTTPS и переключение действующих пользователей. Реальные Gunicorn/Nginx/TLS проверены в приватном стенде; ошибки/откат server_apply — внешними заглушками.
- Screen reader, полный WCAG-аудит, настоящий Safari/iOS и устройства с сенсорным вводом.
- Промышленная длительная многопользовательская HTTP-нагрузка, рабочий объём backup/restore, отказ ОС и удалённая PostgreSQL с verify-full. Текущая HTTP-проверка ограничена восемью пользователями и локальным окружением.
- Перенос прежних DEV/PROD не входит в Cold Start. Существующие базы и реальный сервер не изменялись.

Критерии локального RC пройдены. Промышленный запуск оценивается отдельно по серверной приёмке.
