# Эксплуатация VEQTA

Рабочий сервер: `pg-analytics`. Канонические файлы инфраструктуры и последовательность создания окружений описаны в [deployment.md](deployment.md). DEV и PROD независимы по БД, секретам, сервисам и каталогам.

## Состояние

```bash
sudo bash /opt/veqta-dev/scripts/server_verify.sh dev
sudo bash /opt/veqta-prod/scripts/server_verify.sh prod
sudo journalctl -u veqta-dev.service -n 80 --no-pager
sudo journalctl -u veqta-prod.service -n 80 --no-pager
sudo nginx -t
```

Проверка HTTPS внутри `server_verify.sh` направляется на loopback с правильным именем хоста, не требует внешнего DNS, проверяет login, CSS и `Secure` у CSRF-cookie. Реальная проверка в браузере и ролей пользователей проводится отдельно.

## Обновление

Исходный код обновляет оператор из разрешённого GitHub-коммита. У systemd-пользователей нет GitHub-токенов. Перед обновлением PROD: проверенный коммит, контроль миграций, резервная копия и план восстановления; после обновления — `server_apply.sh prod` и `server_verify.sh prod`. Для DEV команды аналогичны, но запускать их нужно отдельно. Опция `--migrate` применяет изменения схемы только по явному решению администратора.

После нового релиза `server_apply.sh` устанавливает зафиксированные зависимости, проверяет Django, собирает статику, применяет конфигурации и перезапускает сервис. Перезапуск может кратковременно прерывать запросы; скрипт проверяет готовность перед приёмкой HTTPS.

## Данные и секреты

`.env`, кадровые файлы, дампы и результаты импортов **никогда не коммитить**. Файлы `/etc/veqta/dev.env` и `/etc/veqta/prod.env` принадлежат root, группы `veqta-dev` и `veqta-prod`, права `0640`. У PROD и DEV разные ключи Django и пароли баз. Не переносить кадровые данные TEST в PROD без отдельного решения.

Резервные копии БД, если создаются, хранить отдельно с ограничением доступа. Проверка восстановления выполняется в отдельной пустой базе. Наличие `.dump` без пробного восстановления не доказывает пригодность копии. Никаких автоматических очисток или скрытых импортов в серверных скриптах нет.

## Пользователи и безопасность

Пользователи, блокировки, группы и права — через штатный Django Admin. Внутренние учётные записи не требуют e-mail. Проверяйте разграничение организаций, закрытие заявок и запрет правок закрытых записей после каждого релиза. Gunicorn доступен только на `127.0.0.1` через Nginx с HTTPS; у обоих контуров отдельные cookie-имена и включён флаг `Secure`.
