# Эксплуатация

PROD запускается через `veqta.service`; Nginx принимает HTTPS и отдаёт статику. Файл `/etc/veqta/prod.env` доступен только root и группе veqta. Исходники не должны хранить реальные настройки и кадровые файлы.

## Проверка состояния

```bash
sudo systemctl status veqta --no-pager
sudo journalctl -u veqta -n 100 --no-pager
sudo nginx -t
curl -I https://portal.example.org/login/
```

Домен замените своим. Ожидается ответ 200 на форму входа и перенаправление на вход при обращении к защищённой странице без сессии. Ошибки подключения к БД исправляются в настройках своего контура, а не переключением на чужую базу.

После изменения настроек или кода выполните миграции и collectstatic в нужном окружении, затем `sudo systemctl restart veqta`. Перед последующими миграциями нужна актуальная резервная копия. Первичная `veqta_initialize` повторно к непустой схеме не применяется. Заменять её миграцией с --fake нельзя.

## Резервные копии

Копия PostgreSQL содержит кадровые данные и историю. Она хранится с ограниченным доступом и не включается в Git. Конфигурация с секретами копируется отдельно защищённым способом. Частоту и срок хранения определяет владелец системы.

Из оболочки с загруженным PROD-окружением:

```bash
umask 077
mkdir -p private/backups
PGPASSWORD="$DB_PASSWORD" pg_dump --host="$DB_HOST" --port="$DB_PORT" --username="$DB_USER" --dbname="$DB_NAME" --format=custom --file="private/backups/veqta_prod_$(date +%Y%m%d_%H%M%S).dump"
```

Команда не передаёт пароль аргументом pg_dump. Успех проверяется кодом завершения и пробным восстановлением; наличие файла само по себе этого не доказывает. Для удалённого сервера сохраняйте настройки TLS и сертификата libpq.

## Пробное восстановление

Восстановление проверяется в отдельной пустой базе администратором PostgreSQL. Работающий контур не очищается. Пример для выбранного файла копии:

```bash
sudo -u postgres createdb --owner=veqta_prod veqta_restore
sudo -u postgres psql -X -v ON_ERROR_STOP=1 --dbname=postgres -c 'REVOKE ALL ON DATABASE veqta_restore FROM PUBLIC'
sudo -u postgres pg_restore --exit-on-error --no-owner --no-privileges --role=veqta_prod --dbname=veqta_restore /secure/path/veqta_prod.dump
```

Путь копии должен быть доступен postgres. Проверьте таблицы, количества, функции и триггеры в восстановленной базе. Конфигурация приложения по умолчанию отвергнет имя veqta_restore: пробное восстановление не должно незаметно стать рабочим контуром. Для реального переключения нужен отдельный согласованный порядок остановки сервиса и замены базы. Не восстанавливайте данные поверх существующей схемы и не отключайте защитные триггеры.

## Пользователи и импорт

Доступ меняется в штатном Django Admin через активность пользователя, группы и разрешения. При блокировке используется is_active. Смена пароля работает через штатную форму Django; отправка почты не настроена.

При импорте сохраняйте исходный архив в защищённом месте по принятому в организации сроку хранения. Не добавляйте кадровые CSV и dry-run с GUID в Git. Подтверждайте дату источника и изменения состава справочника до apply.

Сервис не включает отдельный планировщик, автоматическое принятие выгрузок или очистку бизнес-истории. Эти действия не следует добавлять через прямые SQL-обходы ограничений.
