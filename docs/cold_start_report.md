# VEQTA: архитектура и проверка Cold Start

Исходный `main`: `b33f6e0443d4984be9c64fba2ad63067ba3b0db1`.
Коммит реализации: `c08e86592b53e161f526b4ecf3476abfc41558d4`.
Инструкции и этот отчёт сохранены следующим коммитом. Полный итоговый SHA указан в результате выполнения и в истории Git. Опубликованная история не переписывалась, Pull Request не создавался.

Работа выполнена на отдельных локальных PostgreSQL. Действующие DEV/PROD, их службы, базы и данные не изменялись.

## Что требовало исправления

Предыдущий вариант достигал окончательной модели через старую начальную схему и `0002_managed_directories`. Новая установка сначала создавала уже ненужные поля и фиксированный список организаций, затем переносила их. Для выбранного Cold Start эта цепочка была лишней.

Название организации дублировалось у Employee и RequestEmployee; у Request историческое поле называлось как актуальное значение. Поля периода импорта всегда оставались пустыми, поскольку текущие три CSV не содержат периода табеля. Дополнительно сохранялись флаг актуальности отдельной записи парсера, равный true, и счётчик, всегда равный длине набора сотрудников.

Кадровые снимки строились в Python, а SQL защищал их от правок только в закрытой заявке. Снимки позиции уже фиксировал PostgreSQL. Это давало два разных механизма фиксации истории. Загрузчик каталога вручную повторял часть правил ModelForm. Расчёт повторов был обёрнут дополнительными функциями и неиспользуемым одиночным HTTP-маршрутом. Лимиты повторялись в резервных значениях JavaScript.

## Итоговые модели и именование

| Объект | Окончательное назначение |
|---|---|
| Organization | Внутренний ID, отображаемое name, устойчивый external_id 1С, последнее source_name, requests_enabled |
| Employee | GUID, актуальные кадровые атрибуты, FK организации и обязательный last_seen_import; без строковой копии организации |
| EmployeeImport | Хеши, количества, время приёма и обязательная подтверждённая source_exported_at; без полей периода |
| WorkwearItem | Код, название, категория, срок, порядок и активность; ежедневное управление через Admin |
| Request | FK организации и snapshot_organization_name, статус, версия, автор и завершение |
| RequestEmployee | FK заявки, сотрудника и организации, неизменяемые кадровые snapshot_*; без дополнительной строки organization_name |
| RequestAssignment | FK участника/позиции и неизменяемые снимки кода, названия, категории и срока |
| WorkwearEvent | Независимый номер заявки и неизменяемая запись события; удаление черновика не удаляет историю |

Модели оставлены в пространстве имён Workwear без дополнительных префиксов. Python использует PascalCase для классов и snake_case для полей/функций. ForeignKey и `<field>_id` обозначают объект и внутренний ключ, external_id — ключ источника, snapshot_* — историческое значение. JSON использует snake_case; имена CSV 1С остаются на границе импорта.

В заголовке заявки, участнике, истории и журнале создания возвращается snapshot_organization_name. В результате поиска Employee organization_name означает актуальное отображаемое название из Organization. Остальные краткие поля участника и назначения — представление соответствующих сохранённых снимков; они не читаются из текущего каталога задним числом. Backend и frontend изменены согласованно.

source_name сохранён намеренно: он показывает происхождение записи, позволяет сопоставить вручную созданную организацию и не перезаписывает имя, установленное администратором. Название не используется как доказательство идентичности. Неизвестная организация принимается по orgExtId с запрещённым созданием заявок. Повторный импорт не создаёт дубли; изменение внешней организации существующего GUID отклоняется.

## Штатные механизмы и удалённые конструкции

Для пользователей и разрешений сохранены Django Auth, UserAdmin, User, Group, Permission. Справочники редактируются стандартными ModelAdmin и ModelForm, с раздельными add/change/delete/view permissions. Рабочие заявки и технические таблицы не открыты для свободного редактирования в Admin.

CLI каталога вызывает WorkwearItem.full_clean, как ModelForm Admin: общие валидаторы и декларативные CHECK остаются у модели. В CLI дополнительно проверяются только контракт CSV, дубли внутри файла и идемпотентность загрузки. Собственные роли, административная панель, универсальные справочники или настройки в JSON не добавлялись.

Удалены:

- `workwear/migrations/0002_managed_directories.py` и перенос старых данных;
- `tests/upgrade.py`, проверявший только старую цепочку;
- прежний отчёт о переходе; его содержание остаётся в истории Git;
- Employee.organization_name и RequestEmployee.organization_name;
- EmployeeImport.coverage_start/coverage_end и их ограничение;
- Person.organization_name, Person.current и ParsedBatch.current_count;
- поддержка недатированных прежних импортов и параметр acknowledge-undated-previous;
- kwargs-адаптер старого табельного импорта;
- `services.repeat_warnings_for`, `services.repeat_warnings_for_pairs`, повторный экспорт RepeatWarning;
- одиночный маршрут `ui/requests/<id>/repeat/`, не использовавшийся интерфейсом;
- `_latest_import`, `shortItem` и повторные числовые fallback-лимиты JavaScript.

`repeats.scan_repeats` остался единственной реализацией расчёта. Сервисные бизнес-операции с правами, транзакцией, версией и аудитом сохранены. Разделение Portal, API, импорта, сервисов и интерфейса не заменялось универсальными обёртками над ORM.

Секреты, адрес PostgreSQL, домены, HTTPS, cookies и параметры процессов остаются конфигурацией окружения/развёртывания. В PostgreSQL и Admin находятся предметные справочники. Статусы, права, межтабличная целостность, версии, блокировки и технические бюджеты операций остаются кодом и ограничениями БД. Примеры серверной конфигурации не менялись в этой работе; новый сервер подготавливается отдельно.

## Окончательная начальная миграция

В Workwear остаётся одна `0001_initial`. Декларативная часть создана из окончательных моделей штатным makemigrations. Добавлен RunSQL для составных FK и необходимых межтабличных guards. В миграции нет RunPython, преобразования старых данных, отключения триггеров, фиксированных организаций или списка СИЗ.

На новой PostgreSQL сразу создаются 8 предметных таблиц, индексы, стандартные FK/уникальность, CHECK, 10 SQL-функций, 13 триггеров и два составных FK. Зависимость от пользовательской модели задаётся swappable_dependency Django. Обратный SQL описывает удаление собственных объектов; откат развёрнутого окружения с данными в эту проверку не входил.

| Группа ограничений | Что защищает |
|---|---|
| Хеши импорта и ww_import_hash_triplet_uniq | Формат хешей и повтор принятой тройки |
| ww_import_counts_ck | Количество исходных строк не меньше числа сотрудников |
| Organization external_id, ww_org_external_id_ck, ww_org_name_ck | Уникальность/формат внешнего ключа и непустое название |
| Employee GUID, обязательный last_seen_import, ww_employee_required_ck | Устойчивую идентичность, происхождение и обязательные атрибуты |
| ww_emp_id_org_uniq, ww_req_id_org_uniq и составные FK | Совпадение организаций сотрудника, участника и заявки |
| ww_req_status_ck, ww_req_version_ck, ww_req_completion_ck | Допустимое состояние, положительную версию и согласованное завершение |
| ww_member_request_emp_uniq, ww_member_snapshot_ck | Единственного участника и непустой кадровый снимок |
| Код WorkwearItem, ww_item_validity_ck, ww_item_required_ck | Уникальный код, положительный допустимый срок и обязательные атрибуты |
| ww_assignment_member_item_uniq и CHECK снимка назначения | Одно назначение позиции и корректность сохранённого срока/атрибутов |
| ww_event_req_positive_ck, ww_event_type_nonempty_ck | Корректный номер заявки и непустой тип события |
| Identity guards | Неизменность ключей, происхождения заявки, кадровых снимков и снимков позиций |
| Member/assignment guards | Последнюю выгрузку, активность новой позиции и запрет изменения закрытого состава |
| Request guards | Начальный draft версии 1, запрет уменьшения версии, переход ровно на следующую версию, непустое полное завершение |
| Event/структурные guards | Append-only историю и запрет структурного TRUNCATE |

Кадровый снимок теперь заполняет INSERT-триггер, включая bulk_create и прямой SQL. Клиент не может подменить его значениями из запроса; UPDATE снимка запрещён в любом статусе. Заявка и назначения используют тот же принцип. Пустые участники исключаются сервисом до завершения в общей транзакции.

БД защищает данные, но не знает пользователя Django. Права, ожидаемая версия и запись событий проверяются сервисными операциями. Прямые сторонние writers должны соблюдать протокол advisory locks; выдача учётных данных владельца БД обычному пользователю не является поддерживаемым способом работы.

## Документация и границы применения

README, архитектура, установка, развёртывание, справочники, импорт, Workwear, эксплуатация, тестирование и публикация согласованы с Cold Start. Последовательность начинается с нового окружения, заканчивается справочниками и первой заявкой. Пользователи/группы настраиваются через стандартный Admin, администратор создаётся createsuperuser.

Новая 0001_initial не совместима с прежней историей миграций. Её нельзя применять к старому DEV/PROD, имитировать --fake или предварительно очищать базы. Совместимость со старой схемой намеренно не реализована по условию задачи. Переключение окружений и перенос реальных данных не выполнялись.

Не проверены: запуск служб systemd/Nginx на новом целевом сервере, внешняя HTTPS-сеть, другие браузеры, полный аудит accessibility, эксплуатационная отказоустойчивость, восстановление рабочего объёма данных. Удаление/пересоздание действующих баз, применение к PROD и переключение пользователей не выполнялись. Для этих действий нужна отдельная приёмка.
