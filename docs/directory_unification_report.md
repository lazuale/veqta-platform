## Модель и административные формы

Organization содержит внутренний ID, name, уникальный необязательный external_id, source_name и requests_enabled. External_id сопоставляется с orgExtId; после первого заполнения он неизменяем. Display name не определяет идентичность. Неизвестные организации из кадрового источника сохраняются с запретом новых заявок. Старые записи без ID требуется явно связать через Admin; совпадение названия само по себе не объединяет организации.

Employee, Request и RequestEmployee используют Organization с PROTECT. Название источника у Employee может обновляться; имя в Request и кадровые снимки RequestEmployee сохраняются. Принадлежность сотрудника проверяется по ID во всех сервисах и двух составных FK PostgreSQL. Для нового включения БД дополнительно проверяет последнюю принятую выгрузку.

WorkwearItem содержит прежние код, название, категорию, срок, порядок и активность. Код неизменяем; использованную позицию нельзя удалить. RequestAssignment хранит снимок кода, названия, категории и срока, заполненный INSERT-триггером. Прямой SQL не может подменить снимок, создать новое назначение неактивной позиции или изменить завершённую заявку. Версии, атомарность и append-only журнал сохранены.

В штатном Django Admin зарегистрированы только Organization и WorkwearItem. Добавлены русские поля, поиск, списки, фильтры и порядок отображения. Ключи после заполнения доступны только для чтения. Используются штатные add/change/delete/view permissions; право создавать заявки не даёт прав менять справочники. Технические модели Workwear в Admin не зарегистрированы. Подробный порядок первоначального заполнения: [directories.md](directories.md).

API и frontend согласованно используют числовой organization_id. Названия возвращаются как отображаемые снимки. Метаданные отдельно содержат организации для создания и для фильтра реестра; позиции имеют флаг активности. Индекс снимков на клиенте кэшируется по серверному снимку заявки, чтобы отрисовка каждой строки не обходила весь состав. Общий дизайн Workwear не менялся.

## Миграция

Добавлена одна последующая миграция `0002_managed_directories`. `0001_initial` и настройки изоляции контуров не изменены. Миграция создаёт организации только из существующих данных, переносит ссылки пакетными UPDATE, фиксирует доступные атрибуты старых назначений, проверяет количества и соответствия, делает новые поля обязательными и восстанавливает составные FK и guards по ID. Пустая установка остаётся без готовых справочников.

Перенос выполняется одной транзакцией под ACCESS EXCLUSIVE. Guards временно отключаются только внутри неё и включаются до COMMIT. Неоднозначные названия вызывают отказ с полным откатом. События и сведения о завершении не переписываются. Внешние ключи защищают историю от удаления справочников. Проверены отдельные сценарии чистой установки, обновления с завершённой заявкой и отката ошибки.

## Ограничения перехода

- На рабочем объёме данных миграция не запускалась. До применения нужно проверить резервную копию и время переноса на отдельной копии, остановить процессы выбранного приложения и импорта в окно обслуживания.
- У старых организаций нет сохранённого orgExtId. Его задаёт администратор по проверенному источнику до следующей новой выгрузки.
- Старые назначения не содержали снимков каталога. Миграция фиксирует доступные значения на момент перехода; прежние изменения каталога нельзя восстановить без внешних документов или копии БД.
- Возврат схемы к 0001 не поддерживается. Для отката нужны база до перехода и соответствующий SHA; новые записи после перехода надо учитывать отдельно.
- Внешние клиенты API должны перейти на organization_id. Штатный frontend изменён в той же реализации.
- Проверен один браузер. Реальный сервер, systemd/Nginx, другие браузеры и промышленная приёмка в эту работу не входили.
