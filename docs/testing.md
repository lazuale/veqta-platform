# Проверка VEQTA

Проверки выполняются в отдельном окружении DEV с PostgreSQL 18 и вымышленными данными. SQLite не проверяет составные FK, PL/pgSQL, advisory locks и DISTINCT ON и для этого проекта не используется. Пароли и кадровые файлы не входят в репозиторий.

## Регрессия

Из корня проекта с активным venv подготовьте настройки **отдельного тестового DEV**, созданного SQL из deploy/postgresql/dev.sql. Для миграций и создания одноразовой БД нужны реквизиты владельца. Прикладной пароль передаётся только тестовому оркестратору:

```bash
set -a; source .env.dev; set +a
export DB_RUNTIME_PASSWORD=$DB_PASSWORD
set -a; source .env.dev-migrate; set +a
```

Не подставляйте серверные PROD-реквизиты. Эти файлы должны относиться к изолированному тестовому кластеру. `DB_RUNTIME_PASSWORD` не является настройкой работающей службы. Далее:

```bash
python -m pip install --require-hashes -r requirements.lock
python -m pip check
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test tests --verbosity 2 --noinput
```

Django создаёт `test_veqta_dev`, применяет окончательную `0001_initial` и удаляет временную базу по завершении. Перед запуском убедитесь, что под этим именем нет нужных данных. Не используйте --keepdb с другой версией схемы. Если прежний запуск оборвался, сначала проверьте происхождение оставшейся тестовой базы.

TestCase откатывает каждый сценарий без TRUNCATE защищённых таблиц. Триггеры не отключаются. Проверяются жизненный цикл, права Django, Admin, API, импорт, снимки, повторы, конфликт версий, атомарность и прямые SQL-запреты. Нагрузочный сценарий сохраняет и завершает 1000 сотрудников с 30 позициями у каждого и выводит время и число SQL-запросов.

Отдельные тесты серверных сценариев не требуют рабочей БД, root или systemd:

```bash
python -m unittest tests.test_deployment -v
```

Они используют временные файлы, loopback и подставные команды. Это проверка поведения скриптов, а не доказательство установки systemd/Nginx на целевой сервер.

## Проверка Cold Start

Подготовьте **отдельный новый кластер PostgreSQL** с пустой `veqta_dev` и обеими ролями из `deploy/postgresql/dev.sql`. Загрузите настройки владельца и DB_RUNTIME_PASSWORD, как показано выше, затем выполните:

```bash
python -m tests.coldstart
```

Команда сначала сверяет контур и фактическую БД/роль и отказывается от базы с любыми таблицами. Она не очищает существующую схему. После запуска в этой тестовой базе остаются вымышленные данные; рабочий DEV для этой команды не подходит.

Проверяются одна миграция Workwear, пустые предметные таблицы после migrate, 10 SQL-функций, 13 включённых триггеров, два составных FK и отсутствие удалённых полей. Затем соединение закрывается и создаётся заново под отдельной прикладной ролью. Выполняются штатная createsuperuser, вход, формы Admin, создание организации/СИЗ, DRY_RUN и APPLY реального CSV-архива через management-команду и завершение первой заявки через API. Проверяется отказ прикладной роли в DDL, SET ROLE, session_replication_role, отключении триггеров, TRUNCATE, удалении/правке истории, изменении закрытой заявки и добавлении сотрудника чужой организации. SQLSTATE проверяется явно, все 13 guards остаются включены. После этого сверяются migrate --check и makemigrations --check --dry-run.

Переход со старой схемы не входит в контракт: `tests.upgrade` удалён вместе с переходной миграцией. Базы прежних окружений не используются.

## Конкуренция и браузер

```bash
python -m tests.acceptance
```

Этот сценарий создаёт отдельную `test_veqta_dev` и отказывается от уже существующей. Два разных пользователя с одной версией должны дать одну успешную запись и один конфликт, без частичного состава или лишних событий. Запускайте его после обычных тестов, последовательно, поскольку имя временной БД общее.

Для браузера нужны дополнительные зависимости:

```bash
python -m pip install --require-hashes -r requirements-browser.lock
python -m playwright install chromium firefox webkit
python -m tests.acceptance --browser
```

Можно использовать установленный Chromium или Headless Shell:

```bash
python -m tests.acceptance --browser --browser-executable /usr/bin/chromium
```

Временную базу создаёт владелец; после migrate ей выдаются DML-grants прикладной роли. Временный HTTP-сервер слушает только loopback и подключается как veqta_dev. Его окружение не содержит пароля владельца. `config.testing` включает DEBUG для раздачи статики, разрешает тестовые hosts и выключает Secure cookies только в этом процессе. Серверные настройки контуров не меняются.

Проверяются вход, Portal, профиль, штатная смена пароля, создание заявки, массовый подбор, назначения, сохранение, матрица, завершение, возврат и ширина 390 px. Через нативные формы Admin создаются организация, позиция со сроком 90 дней, группа и пользователь со стандартным разрешением просмотра. Отдельный сеанс проверяет права нового пользователя. После переименования и отключения позиции закрытая заявка должна сохранить прежние атрибуты. Ошибки JavaScript и неожиданные HTTP-ошибки завершают проверку отказом.

### Расширенная приёмка матрицы

```bash
python -m tests.acceptance --browser --matrix --artifacts test-results/rc
```

Для других движков используйте `--engine firefox` и `--engine webkit`, задавая отдельный `--artifacts` каждому запуску. Выполняйте их последовательно, поскольку имя тестовой БД общее. Одни и те же базовые и расширенные сценарии выполняются выбранным движком. Удержание ответов использует стандартный page.route Playwright, без Chromium CDP.

Для своего Chromium добавьте `--browser-executable /usr/bin/chromium`. Флаг `--matrix` можно запускать отдельно от короткого `--browser`. Это тот же сценарий с той же временной БД, а не второй тестовый контур. Все вымышленные данные создаются автоматически. На подготовку заявок с более чем 48 000 назначений и браузерные действия требуется больше времени, чем на обычную регрессию.

`tests/browser_matrix.py` проверяет заявку на 210 сотрудников и 62 позиции: перемежающиеся категории, отключённую позицию с сохранённым назначением, пустую строку и предыдущее завершённое назначение. Отдельные заявки содержат 1, 10, 100, 500 и 1000 сотрудников с 30 позициями у каждого. Тест сверяет пары сотрудник/позиция в DOM, API и PostgreSQL, сохранение после перезагрузки, переключение списка/матрицы/карточки, массовое добавление и удаление, три страницы строк и колонок, сохранение выделения и адресность обновления DOM.

Клавиатурная проверка включает Tab, Shift+Tab, стрелки, Home/End, Ctrl+Home, PageUp/PageDown, Enter/Space, обход недоступных ячеек, один tabindex=0 и видимость фокуса за закреплёнными колонками. Снимки до и после прокрутки создаются для 1920×1080, 1440×900, 1366×768, 1024×768, 768×1024 и 390×844. Автоматические проверки геометрии дополняются просмотром PNG; тест сам по себе не оценивает визуальный дизайн.

Отдельно проверяются статусы массового подбора, совпадающие ФИО, частичный номер, выбор между запросами и вкладками, отмена незавершённого чтения, продолжение/отказ/сохранение при выходе. Playwright намеренно возвращает HTTP 500, обрывает запись и чтение после успешного COMMIT, открывает два редактора одной версии. Проверяются сообщение об ошибке, отсутствие ложного успеха, состояние БД и безопасный повтор. Ожидаемые 500/409 учитываются отдельно; неожиданные HTTP-ошибки и ошибки JavaScript завершают прогон отказом.

В папке `--artifacts` остаются PNG, `matrix-results.json`, `matrix-performance.json`, `matrix-accessibility.txt` и `concurrent-service-results.json`. Последний содержит времена открытия, перехода к матрице, пагинации, изменения ячейки, массового снятия позиций у показанных сотрудников и сохранения, число HTTP/API-запросов по маршрутам, полное число элементов DOM и SQL-запросы временного сервера. Их считает middleware, включённый только в config.testing; отдельные контрольные ORM-запросы теста в этот счётчик не входят. Время сохранения включает получение подтверждённого состава, проверку повторов и контрольную сверку API/БД; это не длительность одного SQL-запроса. Используется локальный runserver, поэтому результаты не являются нагрузочным испытанием промышленного сервера. В JSON записаны фактически выбранный движок и его версия. Наличие файла другого движка не считается подтверждённым прогоном.

История предыдущих назначений проверяется через карточку и просмотр старой заявки. Кнопка «История операций» открывает журнал самой заявки. Дополнительный сценарий `event-journal` сверяет 31 событие на двух страницах с PostgreSQL, проверяет причины возврата как текст, фокус и Tab, чтение без права изменения, отказ без `view_workwearevent`, HTTP 500, некорректный JSON-контракт, повтор загрузки и отмену незавершённого чтения. Несохранённые назначения и основной DOM должны оставаться прежними. Снимки журнала создаются для 1440×900 и 390×844. Вместе с матрицей выполняются 13 групп сценариев. Дополнительная проверка historical-snapshots назначает одну позицию двум сотрудникам до и после изменения имени, категории и срока штатным Admin. Список, колонки, доступные имена ячеек, карточки, деактивация, завершение и перезагрузка сверяются с собственными снимками в PostgreSQL.

Проверка accessibility проверяет scope=colgroup/col/row, colgroup, headers, caption, имена кнопок и реальное accessibility tree браузера. Дополнительно можно передать `--axe-script /path/to/axe.min.js`; тогда violations WCAG 2 A/AA и 2.1 AA сохраняются в accessibility.json и приводят к отказу теста. В ручной CI используется axe-core 4.11.0. Эти проверки и клавиатура не заменяют приёмку со screen reader и не подтверждают все критерии WCAG.

Перед матрицей выполняются восемь одновременных сервисных сеансов разных пользователей: каждый под реальным прикладным подключением сохраняет 100 сотрудников × 30 активных позиций в своей заявке. Проверяются версия, 3000 назначений и два события каждой заявки; записываются время и число SQL. Это проверка конкуренции локальной PostgreSQL, а не многопользовательская нагрузка промышленного HTTP-сервера.

Системному пользователю с HOME `/nonexistent` задайте доступный cache вне исходников:

```bash
export PLAYWRIGHT_BROWSERS_PATH=/var/cache/veqta/dev-playwright
```

Каталог создаёт администратор с владельцем veqta-dev. Недостающие системные библиотеки устанавливаются отдельно по диагностике Playwright; browser dependencies не требуются работающему приложению.

## Проверка изоляции Unix UID

В одноразовом Linux CI runner выполните `sudo bash tests/linux_permissions.sh`. Тест создаёт синтетический root-owned checkout под `/opt`, проверяет реальные отказы непривилегированного Unix UID `nobody` при записи в исполняемый код/venv и чтении закрытого env, а также отказы проверки доверенных прав при ослаблении владения или group-write. Он не изменяет действующие DEV/PROD и не является проверкой промышленного сервера Ubuntu/systemd.

## Проверка исходников

```bash
python scripts/check_source.py
python -m compileall -q config portal workwear tests scripts
for script in workwear/static/workwear/js/*.js; do
    node --input-type=module --check < "$script" || exit 1
done
git diff --check
```

В составе проверяются допустимые типы файлов, отсутствие приватных ключей, токенов и рабочих выгрузок. Проверка синтаксиса JavaScript не заменяет браузер.

## Приёмка через Gunicorn и Nginx

Для следующего этапа используйте тот же tests.acceptance и ту же одноразовую БД:

```bash
python -m tests.acceptance --browser --matrix --server nginx --engine chromium \
  --http-load --artifacts test-results/https/chromium
python -m tests.acceptance --browser --matrix --server nginx --engine firefox \
  --artifacts test-results/https/firefox
python -m tests.acceptance --browser --matrix --server nginx --engine webkit \
  --artifacts test-results/https/webkit
```

Gunicorn берётся из requirements.lock; нужны Nginx и OpenSSL. Для изолированного бинарного файла добавьте `--nginx-executable /path/to/nginx`. `--browser-executable` и `--axe-script` работают как прежде. Запуски последовательные. Это команда только для тестового кластера, не для рабочего DEV.

`tests.browser_support` запускает Gunicorn с двумя workers и Nginx в собственном временном каталоге, на случайных loopback-портах. Используется существующий шаблон HTTPS-сайта; меняются только адрес/порты, временные пути и цель redirect для тестовой установки. collectstatic выполняется штатной командой. В config.testing выбранного процесса DEBUG=0, Secure cookies=1 и включён HTTPS-прокси. Приложение подключается ограниченной veqta_dev; пароль владельца в дочерний сервер не передаётся. Рабочие настройки и службы не читаются и не меняются. После проверки процессы останавливаются и временные файлы удаляются.

Генерируется однодневный сертификат localhost/127.0.0.1. HTTP-клиент проверяет его через отдельный CA-файл, отказывает недоверенному сертификату и неправильному hostname. Проверяются 301 HTTP→HTTPS, Secure CSRF-cookie, X-Frame-Options, статика и MIME CSS. В изолированных браузерных контекстах `ignore_https_errors=True` нужен для этого самоподписанного сертификата; он не заменяет отдельную проверку TLS и не применяется к рабочим сайтам. Публичный ACME этим тестом не подтверждается.

`--http-load` дополняет матрицу восемью разными HTTP-сессиями. Каждая проходит реальный вход и CSRF, создаёт заявку и одновременно с остальными сохраняет 100 сотрудников × 30 позиций. GET API сверяет все пары; PostgreSQL — пары, версию и события. Повтор того же состава не увеличивает версию. Затем две сессии одной версии получают 200 и stale_version/409 без частичного состава. Роль реального соединения проверяется через диагностический заголовок только config.testing. Это ограниченная HTTP-приёмка, не оценка промышленной ёмкости.

В `http-load-results.json` записаны времена sync, SQL, размер ответа, проверки повторов/конфликта и число вызовов тестового клиента. Внутренние переходы HTTP-клиента после login входят во время входа, а не считаются отдельными вызовами. Браузерные счётчики HTTP/API в matrix-performance.json по-прежнему считаются по фактическим событиям запросов браузера. В `servers/basic` и `servers/matrix` сохраняются server-stack.json и журналы процессов; ключи и сертификаты в результаты не копируются.

## GitHub Actions

`.github/workflows/verify.yml` запускается при push и pull_request. Используются Python из .python-version, PostgreSQL 18.7 в одноразовом контейнере, случайные ключи и две роли. Дополнительно на push проверяются владельцы и права в синтетическом root-owned checkout через sudo. Проверяются установка обоих lock-файлов с hashes, pip check, совпадение requirements.txt/lock, Cold Start под владельцем и прикладные запреты, системные проверки Django, makemigrations, вся регрессия, конкуренция, состав и синтаксис исходников.

Ручной workflow_dispatch дополнительно устанавливает Chromium/Firefox/WebKit, Nginx/OpenSSL и последовательно запускает полную приёмку каждого движка через HTTPS с axe. В Chromium добавлены восемь HTTP-пользователей и конфликт записи; в Firefox/WebKit повторяются те же пользовательские сценарии без повторной HTTP-нагрузки. JSON/PNG прикладываются к запуску на семь дней. Развёртывания и серверных секретов в workflow нет. Статус конкретного Actions-запуска нужно проверять в GitHub; локальная проверка команд не заменяет зелёный удалённый job.
