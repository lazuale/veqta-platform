# Проверки проекта

Тесты используют только синтетические имена, номера и случайные GUID. Они создают отдельную PostgreSQL `test_veqta_dev`. Кадровые выгрузки и утверждённый рабочий каталог в тестах не используются.

## Регрессионный набор

Для проверки перехода со старой схемы отдельно выполните:

```bash
python -m tests.upgrade
```

Команда разрешена только из DEV, создаёт новую `test_veqta_dev` и отказывается от уже существующей. Проверяются чистая установка, переход с завершённой синтетической заявкой и полный откат при неоднозначных организациях. Существующие ID, версии, снимки, история, составные FK и включённые guards проверяются после перехода. Запускайте эту проверку последовательно с обычными тестами: они используют одно имя временной БД.

Из корня проекта с активным venv и загруженным **DEV**-окружением. На сервере это `/etc/veqta/dev.env`, локально — отдельный `.env.dev`. Не меняйте серверные DEBUG, Secure cookies или ключи ради тестов. Пример полного серверного запуска:

```bash
sudo -u veqta-dev bash -c '
    set -Eeuo pipefail
    set -a; source /etc/veqta/dev.env; set +a
    cd /opt/veqta-dev
    .venv/bin/python manage.py check
    .venv/bin/python manage.py makemigrations --check --dry-run
    .venv/bin/python manage.py test tests --verbosity 2 --noinput
    .venv/bin/python -m tests.acceptance
'
```

Отдельная регрессия серверных проверок не требует БД, root или systemd. Она работает только с временными файлами, синтетическими внешними командами и loopback:

```bash
python -m unittest tests.test_deployment -v
```

Она покрывает временный HTTPS-отказ, cookie другого контура, redirect, отказ транспорта/БД, proxy environment, ошибку Git, нефатальный конфликт Nginx и ограниченный renewal hook. Эти тесты входят также в общий Django runner; они не заменяют установку настоящих unit-файлов и reboot.

Эквивалентные локальные команды:

```bash
python -m pip install --no-cache-dir --require-hashes -r requirements.lock
python -m pip check
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test tests --verbosity 2
```

Штатный Django TestCase откатывает транзакцию каждого теста. Защитные триггеры остаются включёнными. Не используйте flush и не отключайте TRUNCATE-защиту ради очистки тестов. Рабочие veqta_dev и veqta_prod не очищаются тестовым набором.

Временная тестовая база удаляется по завершении. Не сохраняйте в ней свои данные и не используйте --keepdb. Если предыдущая проверка аварийно оборвалась, сначала отдельно проверьте, что оставшаяся test_veqta_dev относится именно к тестам; только затем удаляйте её штатными средствами PostgreSQL.

## Конкурентное редактирование

```bash
python -m tests.acceptance
```

Проверка создаёт тестовую схему и запускает две отдельные транзакции с одной ожидаемой версией. Ровно одна запись должна пройти, другая — получить конфликт. Затем проверяются версия, состав и число событий. Существующую test_veqta_dev эта команда не перезаписывает.

## Браузер

Дополнительные зависимости нужны только для испытаний интерфейса:

```bash
python -m pip install --require-hashes -r requirements-browser.lock
python -m playwright install chromium
python -m tests.acceptance --browser
```

При наличии подходящего установленного браузера можно явно указать путь:

```bash
python -m tests.acceptance --browser --browser-executable /usr/bin/chromium
```

Playwright запускает временный сервер только на loopback и в тестовой базе. Пользователь и пароль создаются на время проверки; они не записаны в исходниках. Проверяются вход, переход в Workwear, создание черновика, массовый подбор, назначение СИЗ, сохранение, матрица, завершение, возврат и экран шириной 390 px. Ошибки JavaScript и неуспешные HTTP-ответы приводят к отказу проверки.

`config.testing` явно включает DEBUG=True для раздачи staticfiles только во временном DEV-процессе. Нормальный серверный DEV остаётся DEBUG=0. Конфигурационные subprocess-тесты отдельно нормализуют Secure cookies; результат не зависит от серверного значения этого флага.

Системный пользователь `veqta-dev` имеет HOME `/nonexistent`. Для загрузки управляемого браузера ему нужен отдельный доступный cache, а не каталог HOME:

```bash
sudo install -d -o veqta-dev -g veqta-dev -m 0700 /var/cache/veqta/dev-playwright
sudo -u veqta-dev bash -c '
    set -Eeuo pipefail
    set -a; source /etc/veqta/dev.env; set +a
    cd /opt/veqta-dev
    export PLAYWRIGHT_BROWSERS_PATH=/var/cache/veqta/dev-playwright
    .venv/bin/python -m pip install --no-cache-dir --require-hashes -r requirements-browser.lock
    .venv/bin/python -m playwright install chromium
    .venv/bin/python -m tests.acceptance --browser
'
```

При отсутствии системных библиотек браузера администратор подготавливает их по диагностике Playwright (`python -m playwright install-deps chromium` выполняется с нужными правами и меняет пакеты ОС). На общем сервере сначала оцените этот список; вариант с уже установленным Chromium и `--browser-executable` остаётся доступным. Browser dependencies не требуются для работы приложения и не устанавливаются server_apply.

## Проверка после установки

Войдите обычным аналитиком и проверьте права по таблице в workwear.md. Просмотр всех организаций должен оставаться доступным, а включение сотрудника чужой организации — отклоняться. Проверьте выход, смену пароля штатной формой, конфликт двух вкладок и запрет правок завершённой заявки. После заполнения справочников отдельно проверьте рабочие названия и сроки; синтетический тест не подтверждает правильность выбранных оператором значений.
