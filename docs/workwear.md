# Работа с заявками на спецодежду

Назначение модуля — быстро подготовить и завершить заявку. Складские остатки, выдача со склада и расчёт удержаний в него не входят.

## Пользователи и права

Пользователи и группы создаются в штатном `/admin/`. Отдельного механизма учётных записей нет. Группы не создаются миграцией: администратор задаёт их в своём контуре.

| Назначение доступа | Разрешения Workwear |
|---|---|
| Просмотр заявок | `view_request` |
| Подбор и просмотр сотрудников | `view_employee` |
| Просмотр каталога | `view_workwearitem` |
| Просмотр истории | `view_workwearevent` вместе с `view_request` |
| Подготовка заявок | предыдущие права, `add_request`, `change_request` |
| Удаление черновика | `delete_request` |
| Возврат завершённой заявки | отдельное `reopen_request` |

Аналитик с правом просмотра видит заявки всех организаций. Права изменения проверяются отдельно. Возврат в работу выдаётся администратору или уполномоченному ведущему аналитику через `reopen_request`. Название группы само по себе права не предоставляет.

## Жизненный цикл

Заявка создаётся как `draft`. Для неё выбирается одна организация: АЛМАЗ ООО, АВМ ООО или УПРАВЛЕНИЕ КАРЬЕРАМИ ООО. Изменить организацию существующей заявки нельзя.

Подбор принимает ФИО или актуальный табельный номер 1С. Массовый список состоит из одного столбца, по записи на строку. Новое включение допускается только для сотрудника нужной организации из последней принятой выгрузки. Постоянный идентификатор — GUID; однофамильцы не объединяются. Старые участники уже сохранённых заявок остаются доступными по своим снимкам.

Назначения можно менять в карточке, списке или матрице, в том числе массово для выбранных сотрудников. Локальные изменения попадают в БД после сохранения. Верхний технический предел — 1000 сотрудников и 30 позиций на каждого; утверждённый рабочий каталог содержит 11 позиций.

При завершении сотрудники без назначений автоматически исключаются. Перед подтверждением показано их количество. Если после исключения заявка пуста, завершение отменяется целиком, включая исключение участников. У каждого оставшегося участника должны быть назначение и заполненный снимок ФИО, номера и организации.

Завершённая заявка имеет состояние `closed`, дату и автора завершения. Изменение состава, позиций и самой заявки запрещено в сервисах и PostgreSQL. Возврат разрешён только с отдельным правом и актуальной версией; он очищает текущие поля завершения, а прежнее завершение остаётся в истории.

Любое фактическое изменение состава или назначений увеличивает версию. Конкурирующая запись со старой версией получает конфликт, а её данные не записываются. Неизменённое сохранение не увеличивает версию. Нельзя автоматически повторять неудачную запись, не прочитав результат сервера.

## Повторные назначения

Предупреждение рассчитывается для точного сотрудника и позиции по последней подходящей завершённой заявке. Сравниваются календарные даты Europe/Moscow: год — 365 дней, два года — 730. В дату истечения срока предупреждения уже нет. Будущие местные даты не скрывают предыдущее действующее назначение. Предупреждение не блокирует повторную выдачу.

## HTTP

Страница модуля — `/workwear/`. API имеет префикс `/workwear/api/` и использует штатную сессию Django и CSRF. Записывающие запросы принимают application/json. Снимки сотрудников клиент не задаёт: их строит сервер.

| Маршрут после префикса | Назначение |
|---|---|
| `session/` | GET: имя вошедшего пользователя и токен CSRF |
| `requests/` | GET: заявки; POST: создать черновик |
| `requests/<id>/` | GET: полная заявка; DELETE: удалить черновик |
| `requests/<id>/members/`, `assignments/` | POST: отдельное включение/назначение |
| `requests/<id>/complete/`, `reopen/` | POST: завершение/возврат |
| `ui/metadata/`, `ui/requests/`, `ui/employees/` | GET: настройки интерфейса, реестр и поиск |
| `ui/resolve/` | POST: разрешение до 100 строк подбора |
| `ui/requests/<id>/bulk-add/` | POST: атомарное включение сотрудников |
| `ui/requests/<id>/sync/` | POST: полный состав, expected_version и обязательный finish |
| `ui/requests/<id>/repeat-scan/` | POST: до 1200 уникальных пар сотрудник/позиция |
| `ui/requests/<id>/events/` | GET: история с пагинацией |
| `ui/requests/<id>/employees/<employee_id>/history/` | GET: предыдущие завершённые назначения |
| `ui/requests/<id>/reopen/` | POST: возврат с причиной |

Обычный JSON ограничен 64 КиБ, sync — 1 МиБ. Реестр отдаёт до 100 заявок за страницу, поиск — до 40 сотрудников. Основные ответы об ошибках: 400 — неверные параметры, 401 — нет сессии, 403 — нет права или CSRF, 404 — объект отсутствует, 409 — конфликт версии или целостности, 413 — превышен размер, 405 — неверный метод. Точные параметры отдельных маршрутов указаны в docstring соответствующего представления и проверяются тестами.
