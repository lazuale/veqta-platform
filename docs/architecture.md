# Архитектура и устройство кода

Приложение — один Django-проект с общей PostgreSQL внутри каждого контура. Portal не импортирует предметные сервисы Workwear. Права пользователей основаны на штатных User, Group, Permission и Django Admin.

| Часть | Ответственность |
|---|---|
| `config/settings.py`, `database.py` | Проверка настроек и адресата служебных операций |
| `portal/views.py`, `context_processors.py` | Страницы, профиль и доступная навигация |
| `workwear/models.py` | Поля моделей, индексы, декларативные ограничения |
| `workwear/migrations/` | Одна окончательная начальная схема, составные FK и SQL-защита |
| `workwear/admin.py` | Штатное управление организациями и каталогом |
| `services.py` | Права, блокировки, отдельные операции, аудит |
| `sync.py` | Атомарное сохранение полного локального черновика |
| `eligibility.py`, `ingest_lock.py` | Допуск новых сотрудников и блокировка справочника |
| `employee_lookup.py`, `ui_api.py` | Подбор сотрудников, реестр и API интерфейса |
| `repeats.py` | Единый расчёт повторных назначений |
| `api.py`, `urls.py` | HTTP-методы, CSRF, JSON и отображение ошибок |
| `importers/directories_1c.py` | Чистый разбор трёх CSV без Django и БД |
| `importers/acceptance.py` | Транзакционная публикация принятого справочника |

## Модели

`EmployeeImport` хранит хеши трёх исходных файлов, время приёма, подтверждённую дату источника и количества. Дата источника обязательна. Полей периода нет: три CSV не передают период табеля.

`Organization` хранит постоянный внутренний ID, отображаемое название, уникальный необязательный `external_id` 1С, последнее название источника и признак разрешения новых заявок. Наличие организации в импорте не включает этот признак. Имя не служит ключом.

`Employee` хранит постоянный GUID и актуальные кадровые атрибуты. GUID и организация неизменны; табельный номер разрешено исправлять. `last_seen_import` показывает, в какой принятой выгрузке сотрудник присутствовал.

`WorkwearItem` — управляемый каталог с неизменяемым кодом, названием, текстовой категорией, сроком в календарных днях (1–32767), порядком и активностью. Категории не имеют фиксированного набора; отдельная модель для них не требуется. Ограничение 365/730 относилось к первоначальному наполнению: алгоритм сравнивает целое число прошедших дней, не зависит от названия и проверен также на других сроках.

`Employee`, `Request` и `RequestEmployee` связаны с `Organization` через FK с PROTECT. `Employee` не дублирует название организации: актуальные имя и название источника находятся в `Organization`. `Request.snapshot_organization_name` — неизменяемое название при создании заявки. У `RequestEmployee` есть только FK организации и кадровые `snapshot_*`, без второй строковой копии организации.

`Request` содержит организацию, состояние, версию, автора и завершение. `RequestEmployee` связывает сотрудника с заявкой и хранит снимок кадровых атрибутов. INSERT-триггер берёт снимок из Employee и отображаемого названия Organization. Python не дублирует заполнение; UPDATE снимка запрещён даже в черновике. `RequestAssignment` связывает участника и позицию СИЗ и хранит неизменяемый снимок кода, названия, категории и срока. Снимок заполняет INSERT-триггер, включая bulk_create и прямой SQL. Повторы используют срок прошлого назначения, а не текущее значение каталога. Уникальные ограничения не допускают повторного участника или той же позиции у участника.

`WorkwearEvent` хранит номер заявки, автора, время, тип и детали события. Обязательного FK на заявку нет, поэтому удаление черновика не удаляет его историю. Поля события не меняются после вставки.

## Транзакции

Все изменения проходят через сервисы. Сначала проверяются права, затем берётся общая advisory-блокировка справочника и блокировка строки заявки через SELECT FOR UPDATE. Версия проверяется под блокировкой. Состав, назначения, новая версия и событие фиксируются одной транзакцией. Ошибка любого шага отменяет всю операцию.

Публикация 1С берёт исключительную advisory-блокировку того же справочника. Такой порядок не позволяет одновременно принять новый справочник и включить сотрудника по устаревшей проверке.

SQL-защита работает и при обходе ORM. Она не заменяет авторизацию сервиса: PostgreSQL не знает прикладного пользователя Django. Владельцу БД и суперпользователю нельзя выдавать прикладные права напрямую, считая их обычными пользователями.

## Полномочия PostgreSQL

В каждом контуре две роли без членства друг в друге. `veqta_ENV_owner` владеет базой, схемой, таблицами, последовательностями и функциями и выполняет штатный Django migrate. `veqta_ENV` получает CONNECT, USAGE схемы, SELECT/INSERT/UPDATE/DELETE таблиц, USAGE/SELECT последовательностей и EXECUTE функций. Она не получает CREATE, TEMP, TRUNCATE, права владельца или управление ролями. CREATEDB есть только у владельца DEV для Django-тестов.

Default privileges настраиваются до migrate для конкретного владельца. EXECUTE от PUBLIC отзывается без IN SCHEMA, поскольку глобальный стандартный grant нельзя снять локальным revoke. Все функции Workwear остаются SECURITY INVOKER. Отдельного исполнителя миграций и третьей роли нет: для этой схемы они дублировали бы владельца.

Триггеры защищают целостность, а разрешения Django — действия конкретного пользователя. Прикладные реквизиты PostgreSQL позволяют штатные переходы жизненного цикла; они не заменяют проверку `reopen_request` в сервисе. Владельцы и администраторы PostgreSQL остаются доверенными операторами. Пароль владельца отсутствует в процессе обычной службы. Unix UID `veqta-dev`/`veqta-prod` может читать и исполнять root-owned checkout/venv, но не может изменять Git, Python-код и библиотеки. Root запускает штатный Django `migrate` с отдельным закрытым env владельца PostgreSQL и очищенным окружением (`env -i`); обычный Gunicorn не получает этих полномочий. Компрометация root или доверенного источника администратором остаётся вне этой границы угроз.

## Защита PostgreSQL

| Функция | Триггеры и правило |
|---|---|
| `ww_guard_employee_identity` | `ww_employee_identity_bu`: запрет изменения id, GUID и организации |
| `ww_guard_request_identity` | `ww_request_identity_bu`: неизменность происхождения заявки |
| `ww_reject_event_change` | `ww_event_no_update_delete`, `ww_event_no_truncate`: неизменность истории |
| `ww_guard_member_write` | `ww_member_write_biud`: неизменность связи и снимка, захват кадровых атрибутов при INSERT, запрет изменений закрытого состава и проверка последней выгрузки |
| `ww_guard_assignment_write` | `ww_assignment_write_biud`: неизменность связи/снимка, запрет изменений закрытых назначений, проверка активности и заполнение снимка при INSERT |
| `ww_guard_request_lifecycle` | `ww_request_lifecycle_bud`: запрет уменьшения версии, переход ровно на следующую версию, полнота завершения, запрет удаления и правок закрытой заявки |
| `ww_reject_structure_truncate` | `ww_request_no_truncate`, `ww_member_no_truncate`, `ww_assignment_no_truncate` |
| `ww_guard_request_insert` | `ww_request_initial_bi`: создание только черновика версии 1 для разрешённой организации, фиксация её названия |
| `ww_guard_organization_identity` | `ww_organization_identity_bu`: неизменность id и уже заданного внешнего ключа |
| `ww_guard_item_identity` | `ww_item_identity_bu`: неизменность id и кода позиции |

Составные FK `ww_member_req_org_fk` и `ww_member_emp_org_fk` независимо требуют совпадения `organization_id` заявки, участника и сотрудника. Стандартные FK защищают ссылки и удаление используемых справочников. Уникальные ограничения защищают GUID, внешние ID, коды, участников и назначения. CHECK отвечают за непустые обязательные атрибуты, сроки, хеши импорта, согласованность состояния и полей завершения.

`0001_initial` создаёт сразу окончательные поля, индексы, 10 функций, 13 триггеров и оба составных FK. В ней нет переноса данных, отключения guards или промежуточных ALTER старой схемы. Обратный SQL удаляет собственные FK, триггеры и функции в порядке зависимостей. Новая схема проверяется только на пустой БД; --fake и применение к прежней истории не поддерживаются.

## Именование и границы модулей

Модели используют пространство имён приложения `workwear`; дополнительные префиксы Workwear для каждой модели не нужны. ForeignKey называется по объекту, его внутренний ID — `<field>_id`. `Organization.external_id` — ключ 1С, `name` — отображаемое название, `source_name` — последнее название источника, `snapshot_*` — исторические значения. Названия источника не копируются на каждого сотрудника.

JSON использует snake_case. `orgExtId` и другие имена 1С остаются только на границе CSV. В заявке и истории явно возвращается `snapshot_organization_name`; в поиске сотрудника `organization_name` означает актуальное отображаемое имя. Кадровые `full_name`, `personnel_number`, `position_name`, `department_name` в объекте участника — проекция его сохранённых снимков, а не чтение актуального Employee. В назначении `name`, `code`, `category`, `validity_days` аналогично берутся из снимка позиции.

Имена собственных ограничений и индексов используют префикс `ww_`, сущность и назначение; функции — `ww_guard_*`/`ww_reject_*`, триггеры — сущность и операция. Штатные имена таблиц Django не переопределяются. SQL нужен для неизменяемости и межтабличных правил, которые CHECK и обычный FK не выражают.

`repeats.scan_repeats` — единственная точка расчёта повторов. Сервисные операции с транзакцией, авторизацией, версией и аудитом сохранены; обёртки над расчётом, прежний одиночный маршрут повторов и лишний адаптер latest_import удалены. CLI каталога и ModelForm Admin используют `WorkwearItem.full_clean`, включая валидаторы и CHECK модели.

## Конфигурация

Секреты, подключение PostgreSQL, домены, HTTPS, cookies и процессы задаются окружением и файлами развёртывания. Django должен прочитать их до подключения к базе; в Admin они не переносятся. Organization и WorkwearItem — управляемые справочники PostgreSQL. Статусы, разрешения, блокировки, целостность и технические бюджеты операций остаются кодом и ограничениями БД. Универсальной таблицы настроек и собственной системы ролей нет.

## Интерфейс

Portal загружает `tokens.css`, `base.css`, `components.css`, `layout.css`, `portal.css` в этом порядке. Workwear добавляет `app.css`. Общие токены определяют ширину, интервалы, типографику и состояния. Внешних CDN и обязательных внешних шрифтов нет.

`workwear/app.js` собирает модули через явный общий контекст. `core.js` создаёт локальное состояние и HTTP-клиент; `registry.js` ведёт реестр и URL; `editor.js` — локальные назначения; `employees.js` — подбор; `overlays.js` — диалоги и историю; `batching.js` и `paging.js` ограничивают размер чтений; `controller.js` связывает события.

Локальный выбор не равен записи в БД. Сохранение передаёт весь нормализованный состав в sync. Табличные изменения обновляются адресно с сохранением фокуса и прокрутки; переход между экранами может перестраивать основной раздел. Счётчики запросов и AbortController не дают запоздалому ответу заменить новый результат. Проверка повторов пакетная и не принимает решение о запрете выдачи.

Колонка матрицы описывает текущую позицию каталога: название, категорию и явно подписанный текущий срок. `core.assignmentItem` выбирает собственный снимок назначения сотрудника; его имя, категория и срок используются в title/aria-label ячейки, подсказке списка и карточке. Колонка никогда не заимствует первый снимок другого сотрудника. При отсутствии права чтения каталога колонка называется по стабильному ID, а назначения сохраняют свои доступные исторические данные. Индекс каталога кешируется по metadata и подтверждённому снимку; каждое действие не сканирует все 30 000 назначений.

Матрица остаётся HTML-таблицей: colgroup для соседних категорий, scope=colgroup/col/row, явные headers ячеек, caption и aria-pressed кнопок. Самодельного ARIA-grid нет.

Матрица показывает до 100 строк и 30 колонок на странице. Это бюджет DOM; весь состав остаётся в локальном черновике. Выделение сохраняется между страницами, checkbox заголовка относится только к показанным строкам. Заголовки категорий объединяют соседние колонки с одной категорией, сохраняя порядок каталога. Одна категория может встречаться в нескольких группах, если администратор перемежал позиции.

Доступность ячейки определяется в `editor.cellAvailable`: правом изменения, активностью позиции или существующим назначением и отсутствием ожидающей проверки этой пары. Сохранение отдельно блокирует все элементы через `core.setBusy`. Контроллер ведёт одну точку входа Tab и пропускает недоступные ячейки при навигации. После снятия неактивной позиции фокус получает доступная ячейка той же строки. Одиночное действие заменяет затронутую строку, сохраняя основной контейнер, таблицу и остальные строки. Короткие и узкие окна используют вертикальную прокрутку редактора; таблица сохраняет собственную область прокрутки.

Журнал операций использует существующий `ui/requests/<id>/events/` и штатные права просмотра. `overlays.loadEvents` загружает только 25 записей текущей страницы. `settings.eventLog` отделён от истории прежних назначений сотрудника и содержит только состояние открытого диалога. AbortController и проверка идентичности этого объекта отбрасывают поздние ответы после закрытия или смены заявки. Ответ проверяется до отображения; ошибка чтения не выдаётся за пустой журнал. Текст автора, причины и описаний экранируется, а чтение журнала не меняет локальный состав и не создаёт события.

Статические пути не содержат имён сборок. Nginx отдаёт Cache-Control: no-cache, чтобы браузер перепроверял актуальность модулей после обновления.
